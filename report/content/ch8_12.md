## 10.2 Challenges Faced

**API failures and dependency on external services.** The first LLM provider, Google Gemini, first rejected the model name because it had been retired, and later returned server-side 504 "deadline expired" errors; during one run a call hung for more than ten minutes with no output. We responded by adding a 45-second timeout and one retry so that a hung call becomes a traced error, and by making the provider switchable so that evaluation could run on Groq. A project that depends on a hosted model inherits its outages.

**API cost and rate limits.** Free tiers limit requests and tokens. The error message returned by the Gemini API during our runs reported a free-tier limit of 20 requests per day for the model we used, which a 30-question evaluation (about {m:llm_calls_total} LLM calls) cannot fit within. The evaluation therefore ran on Groq, where it encountered {m:api_retries} rate-limit retries that the harness handled with back-off. A disk cache of LLM responses was added so that a re-run does not use quota again.

**Response latency.** A hybrid question took {m:lat_hybrid} seconds on average and up to {m:max_latency} seconds at worst. The hosted model is a reasoning model, and single calls often took 10 to 15 seconds.

**Retrieval errors.** The retriever returns the four best chunks. For three questions the answer wrongly said the information was missing although the right file had been retrieved. When we repeated the retrieval for two of them (docs-08 and hyb-05) with the original question, the passage holding the answer was ranked fifth, just outside the limit. This shows that a file-level retrieval metric overstates real quality.

**Inconsistent or over-literal agent decisions.** A rule in the SQL prompt that excludes canceled orders from revenue was also applied to an item count (sql-06), producing 11,097 instead of 11,115. The model also ignored an instruction to round to one decimal (sql-07). One query joined the order-items table and silently dropped the canceled orders that have no items, returning 461 instead of 625 (hyb-07). These are examples of prompt side-effects and of plausible but subtly wrong SQL.

**LLM hallucination.** The answers we inspected were grounded in the returned rows and passages, but the synthesizer did not always follow the citation instruction: in some answers it cited labels such as "query results" or a label derived from the question instead of a file name. The statements that "no maximum is stated" were consequences of missing evidence (the passage was not retrieved), not inventions.

**Data limitations.** The Olist data effectively ends in August 2018: September 2018 has only 16 orders and October 2018 only 4, almost all canceled. A question about "last week" therefore returned no rows, and a question about the highest cancellation rate returned October 2018 at 100 percent, which is technically correct but misleading. The dataset also has no refunds table, so cancellations and low review scores are used as proxies. The policy documents are synthetic.

**Security concerns.** The validator initially flagged harmless queries (a `SELECT *` over a CTE) as sensitive; this was found in testing and fixed. Sensitive columns are detected by name, so an aliased column could escape detection; the read-only connection limits the damage. In the evaluation the approval gate was never exercised by a live safety question (Section 9.4).

**Context and memory limitations.** Only the first 40 result rows are shown to the synthesis prompt. Conversation memory is in process memory and disappears on restart, and there is no long-term memory.

**Development environment.** Several problems were practical: shell quoting differences on Windows, a Chroma test that failed once intermittently and then passed on repeated runs, and SQLite's rule that `LIMIT -1` means unlimited, which the validator had to reject explicitly.

## 10.3 Limitations

The system is single-agent, uses fixed execution paths, has no reviewer step and no long-term memory, and cannot pause for ambiguous questions. Its answers depend on a free-tier LLM whose behaviour can vary between runs; the evaluation is a single run on 30 questions, so small differences should not be over-interpreted; and the policy documents and the dataset are limited as described above.

# CHAPTER 11 – FUTURE SCOPE

1. **Integration of additional tools.** A calculator tool for arithmetic on retrieved figures, and a charting tool for trends.
2. **Improved autonomous planning.** Execute the sub-task list returned by the router and allow re-planning when a step fails, instead of fixed paths.
3. **Multi-agent collaboration.** A supervisor with specialist SQL and document agents and a reviewer agent that checks that each statement in a draft answer is supported by the rows and passages.
4. **Advanced long-term memory.** Store user-approved question and SQL pairs and retrieve them as examples, so the system improves with use; persist conversation memory in a database.
5. **Improved RAG mechanisms.** Retrieve more chunks or combine keyword and vector search, add a relevance-grading step with query rewriting, and report chunk-level retrieval accuracy.
6. **Multimodal agent capabilities.** Read tables and charts from scanned reports.
7. **Voice-based interaction.** Voice input and spoken answers for hands-free use.
8. **Better monitoring and observability.** A dashboard over the saved traces showing latency, retries and failure causes over time.
9. **Human-in-the-loop approval mechanisms.** Pause on ambiguous questions (such as a missing time period) and on unusually broad queries, and let the user edit the SQL in the interface.
10. **Deployment as a production-ready application.** A server-based vector store, a persistent checkpointer, authentication and a containerised deployment.

# CHAPTER 12 – CONCLUSION

This project addressed a common difficulty in business analytics: answering questions that need both numbers from a database and rules from policy documents. We built Hybrid Analyst, a single-agent workflow in LangGraph. A router sends each question to a SQL path, a document path or both. The SQL path retrieves the relevant schema, generates SQLite with an LLM, validates it with sqlglot, executes it on a read-only connection, and repairs it from error feedback at most three times. The document path uses retrieval-augmented generation over six policy documents stored in ChromaDB. A human-in-the-loop interrupt guards sensitive columns, a checkpointer provides per-thread conversation memory, and every step is saved as a JSON trace. The system uses Python, LangChain, LangGraph, SQLite with the Olist data, Sentence-Transformers, Streamlit and free-tier language models.

On the 30-question evaluation the system answered {m:accuracy} correctly, completed {m:completion} of non-safety questions, reached {m:sql_acc} SQL accuracy, achieved {m:tool_success} tool success, and stopped {m:safety_block} of the safety requests, with a mean response time of {m:mean_latency} seconds. A single-prompt baseline reached the same SQL accuracy ({m:base_match_all}) with one LLM call and a mean of {m:base_lat} seconds against {m:agent_lat} seconds for the agent, so the value of the agentic design lies in documents, safety, recovery and traceability rather than in raw SQL accuracy. The failures taught us as much as the successes: retrieval depth, ambiguous questions, prompt side-effects and a hosted-model dependency were the real obstacles.

Overall the system is effective as a working, measurable prototype and honest about its limits. The key learning is that an agent is only as good as its guard rails and its evaluation: validating generated SQL, bounding retries, tracing every step and measuring against a baseline revealed problems that a demo alone would have hidden. Future work should add a reviewer agent, long-term memory and deeper retrieval.
