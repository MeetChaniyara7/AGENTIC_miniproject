## 4.1 Overall System Architecture

{fig:arch} shows the major components of Hybrid Analyst. The module and file names in the diagram are the real packages of the project. A question enters through the Streamlit interface and is handed, together with a thread identifier, to the LangGraph agent. Inside the agent, nodes call tools, the tools read from the two knowledge stores (a ChromaDB vector store and a read-only SQLite database), and the three LLM nodes call an external language model through the configuration module. A checkpointer keeps the per-thread conversation, and a trace writer saves one JSON file per question.

## 4.4 Agent Workflow

The complete workflow of one question is described by the following steps, which correspond to the nodes of the graph in {fig:workflow}.

**Step 1:** The user submits a question in the chat page. The page calls the graph with the question and the thread identifier; per-turn state is reset and the question is added to the conversation memory.

**Step 2:** The *router* node understands the objective: the LLM returns a route (SQL, DOCS, BOTH or OUT_OF_SCOPE), a standalone version of the question, a short list of sub-tasks and a reason.

**Step 3:** The route decides the plan. DOCS goes to document retrieval and then to the answer. SQL goes to schema retrieval. BOTH retrieves documents first and then schema. OUT_OF_SCOPE ends with a polite refusal.

**Step 4:** For the SQL part, the *generate_sql* node writes one SQLite query using the retrieved tables, similar example queries and any retrieved business definitions.

**Step 5:** The *validate_sql* node checks the query. If it passes and touches sensitive columns, the *approval* node pauses the graph for a human decision; otherwise the *execute_sql* node runs it on a read-only connection.

**Step 6:** The result is observed: rows, a SQLite error message, or an empty result.

**Step 7:** The decision rules evaluate the result. A validation error, an execution error, or a first empty result sends the error text back to *generate_sql*.

**Step 8:** This repair loop repeats at most three times. After that the graph ends in the *fail* node with a clear message.

**Step 9:** The *synthesize* node writes the final answer from only the returned rows and retrieved passages, and the interface displays the answer, the SQL, the table, the sources and the trace.

# CHAPTER 5 – AGENTIC AI CONCEPTS USED

Only concepts that are actually implemented are described. Where a concept is implemented in a limited form, or not at all, this chapter says so.

## 5.1 ReAct

The SQL path follows a ReAct-style cycle of **reason, act, observe**, but in a simplified form controlled by the graph rather than by free-form LLM output.

- **Reason:** the *generate_sql* node asks the LLM to write a query from the question, the retrieved schema and, on a retry, the previous query and its error.
- **Act:** the *validate_sql* and *execute_sql* nodes run the query through the tools.
- **Observe:** the error message, or the number of rows, is written into the state.
- **Repeat:** an edge function sends the state back to *generate_sql* with the error text, up to three retries.

{fig:trace} shows this cycle on a real question: the first query failed with "no such column: delivered_orders", the error was fed back, and the second query succeeded. The difference from the original ReAct method [1] is that the LLM does not choose which tool to call next or write its own thoughts between actions; the order of tools is fixed by the graph.

## 5.2 Planning

Planning in this project is **task decomposition into predefined paths**. The router node selects one of four routes and rewrites the question. It also returns a list of typed sub-tasks (SQL or DOCS), which is stored in the state and shown in the trace, **but the graph does not execute the sub-task list**; execution follows the route. There is no plan-and-execute loop, no goal-based planner and no dynamic re-planning. A calculator sub-task type was considered and is not implemented.

## 5.3 Tool Calling

Four tools are used. They are invoked by graph nodes: the **tool selection mechanism** is the route chosen by the LLM router together with deterministic edge functions. The LLM does not emit native function-calling requests.

@@TABLE tools

After each tool call the output is stored in the state: retrieved chunks and schema text feed the next prompt, validation errors and execution errors feed the repair prompt, and rows feed the synthesis prompt.

## 5.4 Memory

- **Short-term and conversational memory: implemented.** A LangGraph `MemorySaver` checkpointer stores the state of each thread. The list of messages persists across turns, and the router receives up to the last six previous messages so it can rewrite a follow-up such as "and in 2018?" into a complete question. All other fields are reset at the start of every turn.
- **Retrieval of memory:** the history is placed directly in the router prompt; no similarity search is involved.
- **Limitation:** the checkpointer lives in process memory, so conversations are lost when the application restarts.
- **Long-term memory and vector-based memory: not implemented.** The twelve example queries in the vector store are a fixed, hand-written knowledge base retrieved as examples; the system does not learn new question and SQL pairs from users.

## 5.5 Retrieval-Augmented Generation

The document path follows the pipeline **Documents → Chunking → Embeddings → Vector Database → Retrieval → Context → LLM → Response**, implemented step by step in Section 7.5. Six synthetic Markdown policy documents (refund policy, delivery SLA, seller guidelines, review moderation, data dictionary and metrics glossary) are split by heading and then into chunks of about 500 characters with an overlap of 80, giving {c:n_chunks} chunks. Each chunk is embedded locally with `all-MiniLM-L6-v2` and stored in a persistent ChromaDB collection. At question time the four most similar chunks are retrieved and chunks scoring below 0.30 are dropped, so that an off-topic question returns nothing. The threshold was chosen from measurements: relevant questions scored between 0.39 and 0.77 on their best chunk, off-topic ones between 0.12 and 0.20. The retrieved chunks, with file names and section titles, are placed in the synthesis prompt (and, for hybrid questions, in the SQL prompt as business definitions), and the model must cite the file names it uses. The same mechanism serves the database: schema notes (one entry per table and per column) and example queries are embedded in two further collections so that the SQL generator receives only the relevant tables and the two most similar example queries.

## 5.6 Multi-Agent System

**Not implemented.** The system has one agent (one graph with one shared state). There is no supervisor and specialist agents, no agent-to-agent communication, no task delegation and no reviewer agent. The nodes of the graph are steps of a single workflow.

## 5.7 Human-in-the-Loop

- **Where human intervention occurs.** After a query passes validation, if it reads a sensitive column outside an aggregate function (`customer_unique_id`, `customer_zip_code_prefix`, `geolocation_lat`, `geolocation_lng`), the graph pauses at the *approval* node using a LangGraph interrupt.
- **Why approval is required.** These columns can identify a person or a home area. Counting distinct customers is allowed without approval; listing them row by row is not.
- **What happens after approval or rejection.** The interface shows the SQL with Approve and Reject buttons. Approve resumes the graph and the query is executed. Reject ends the turn in the *fail* node with a message, and the query is never executed. The graph also accepts an edited query, which is validated again before use; the web interface offers only Approve and Reject.
- **Not implemented:** a pause for ambiguous questions (for example, a missing time period) or for unusually broad queries.

# CHAPTER 6 – METHODOLOGY

## 6.1 Input Processing

The Streamlit page passes the question and the session's thread identifier to the graph. A helper creates the input state: it stores the question, appends it to the conversation messages and resets every per-turn field (route, chunks, SQL, rows, retry counter, trace). Only the message list carries over from earlier turns of the same thread.

## 6.2 Task Understanding

The router prompt describes the two information sources, defines the four routes and includes the recent conversation. The LLM returns a JSON object with the route, a standalone version of the question, a list of sub-tasks and a one-sentence reason. The output is parsed tolerantly (code fences and surrounding text are removed). If it is invalid or names an unknown route, the system falls back to BOTH, the safest default, and the trace records the fallback as a failed step.

## 6.3 Task Planning

The chosen route is the plan. DOCS reads documents and writes the answer. SQL retrieves the schema, generates, validates and executes a query, and writes the answer. BOTH does both, reading the documents first so that definitions can inform the SQL. OUT_OF_SCOPE writes a fixed refusal without further LLM calls. The router's sub-task list is recorded for transparency but does not drive execution (Section 5.2).

## 6.4 Reasoning and Decision Making

Decisions between nodes are made by small pure functions of the state, which makes them easy to test. After validation, an error leads to a retry or to failure, a valid query that touches sensitive columns leads to approval, and any other valid query is executed. After execution, an error leads to a retry or to failure, a first empty result leads to one retry with a hint to check filter values, and any other result leads to the answer. The retry counter counts regenerations; after three, the next failure ends the turn. A node exception, a declined approval or an invalid edited query sends the turn to the *fail* node.

## 6.5 Tool Selection

The route selects the tools. *retrieve_docs* runs for DOCS and BOTH; *retrieve_schema*, *validate_sql* and *execute_sql* run for SQL and BOTH. The graph, not the LLM, calls the tools, so the set of possible actions is fixed and auditable.

## 6.6 Task Execution

Before execution the validator parses the query with sqlglot in the SQLite dialect and enforces these rules: exactly one statement, which must be a SELECT (or a UNION of SELECTs); no comments; only allow-listed tables, with no schema-qualified names or table-valued functions; a LIMIT of at most 200, added if missing; and no `LIMIT -1`, which SQLite treats as unlimited. It also flags sensitive-column use. The executor opens the SQLite file read-only and aborts any query that runs longer than ten seconds.

## 6.7 Observation and Feedback

Every result is written to the state. A validator or SQLite error message is inserted into a dedicated slot of the SQL prompt together with the failed query and the instruction to write a corrected query. Every node also appends a trace entry (node name, summary, success flag, duration, number of LLM calls, clipped input and output), and the turn's trace is saved as a JSON file.

## 6.8 Final Response Generation

The synthesis prompt receives the standalone question, the SQL that was run, up to forty result rows and the retrieved passages. It requires the model to use only these, to cite file names in brackets, to state that cancellations and low review scores are proxies for refunds, and to say plainly when results are empty or the documents do not cover the question. The Streamlit page then shows the answer, SQL, table, sources and trace, with friendly banners for errors, empty results and out-of-scope questions.

## 7.3 Tool Implementation

**Tool Name:** `retrieve_docs` (tools/doc_retriever.py)
**Purpose:** Semantic search over the policy documents.
**Input:** a question string, `k` (default 4) and a minimum similarity score (default 0.30).
**Output:** a list of dictionaries with `text`, `source`, `section` and `score`; an empty list when nothing passes the threshold.
**Implementation:** the query is embedded, the Chroma collection is searched, and low-scoring chunks are dropped.
**Role in Agent Workflow:** supplies document evidence for the DOCS and BOTH routes, and lets the agent distinguish "the documents say X" from "the documents have nothing on this".


**Tool Name:** `search_schema` (tools/schema_search.py)
**Purpose:** Give the SQL generator only the relevant part of the schema.
**Input:** the standalone question.
**Output:** one prompt-ready string with the three most relevant tables (descriptions and column meanings) and the two most similar example queries with their SQL.
**Implementation:** tables are ranked by their best-matching table or column entry in the `schema_notes` collection, because a long table description alone scored poorly against short questions; example queries are matched by question similarity.
**Role in Agent Workflow:** the SQL generator never sees the full schema, only what the question needs.

**Tool Name:** `validate_sql` (tools/sql_validator.py)
**Purpose:** Static safety check of generated SQL.
**Input:** a SQL string.
**Output:** a tuple `(ok, cleaned_sql, error, requires_approval)`; error messages are written so that an LLM can repair the query.
**Implementation:** sqlglot parses the SQL in the SQLite dialect and the rules of Section 6.6 are applied. The row-limit rule is shown below.
**Role in Agent Workflow:** the gate between the LLM's text and the database.

@@SNIPPET tools/sql_validator.py::_apply_limit | tools/sql_validator.py: enforcing the row limit

**Tool Name:** `run_sql` (tools/sql_executor.py)
**Purpose:** Execute a validated query safely.
**Input:** a SQL string (and optionally a timeout).
**Output:** an object with `ok`, column names, rows, an error message and the duration; it never raises.
**Implementation:** the database is opened with `mode=ro`, and SQLite's progress handler aborts the query once the deadline passes.
**Role in Agent Workflow:** produces the observation that either feeds the answer or triggers a repair.

@@SNIPPET tools/sql_executor.py::run_sql | tools/sql_executor.py: read-only connection with a timeout

## 7.4 Memory Implementation

**Memory type:** short-term conversational memory (per thread). **Storage mechanism:** a LangGraph `MemorySaver` checkpointer compiled into the graph; each browser session uses its own thread identifier. **Data stored:** the full graph state of the thread after each turn; only the list of messages is meaningful across turns. **Retrieval mechanism:** the router prompt includes the last six previous messages (each clipped to 600 characters). **Influence on future decisions:** the router rewrites follow-ups into standalone questions, which the retrievers and the SQL generator then use. The unit tests verify that a second question sees the first question and its answer, and that a different thread does not. Long-term memory is not implemented.

## 7.5 RAG Implementation

1. **Data collection.** Six synthetic policy documents written for this project (a README in the same folder states that they are synthetic).
2. **Document loading.** All Markdown files in `data/docs/` except the README are read.
3. **Document preprocessing.** Each document is split into sections by its headings; the heading becomes metadata.
4. **Chunking.** A recursive character splitter produces chunks of about 500 characters with an 80-character overlap.
5. **Embedding generation.** `all-MiniLM-L6-v2` runs locally and the vectors are normalised.
6. **Vector database.** A persistent ChromaDB collection named `policy_docs` with cosine distance; ingestion deletes and rebuilds it so that reruns never duplicate chunks.
7. **Similarity search.** The query vector is compared with all chunk vectors.
8. **Context retrieval.** The top four chunks above the threshold are returned with file name, section and score.
9. **LLM response generation.** The synthesis prompt turns the chunks into a cited answer.

@@SNIPPET rag/ingest_docs.py::chunk_document | rag/ingest_docs.py: splitting a document into chunks

## 7.6 User Interface

The interface is a Streamlit page (`app.py`). The sidebar shows the active model, the conversation identifier, a New conversation button and seven example questions. For each answer the page shows the final answer, an expandable SQL block, the result table, the document sources that were retrieved, and an expandable Agent trace with the route, number of steps, retries, LLM calls and timings. When the graph pauses, the page shows the SQL with Approve and Reject buttons and disables the chat box. Errors, empty results, declined approvals and out-of-scope questions are shown as plain-language banners; the technical detail stays in the trace.
