# CHAPTER 1 – INTRODUCTION

## 1.1 Introduction

**Artificial Intelligence (AI)** is the field of computer science concerned with building systems that perform tasks normally requiring human intelligence, such as understanding language, recognising patterns, making decisions and solving problems. **Generative AI** refers to models, most prominently large language models (LLMs), that produce new content such as text, code or images from a prompt. An LLM can write an SQL query or summarise a policy, but on its own it only produces text: it cannot look at a company database, it does not know a company's private rules, and it has no way to check whether what it wrote is correct.

**Agentic AI** goes one step further. An agent wraps a language model in a loop that lets it decide what to do next, use tools to act on the world, observe the results and continue until the goal is met. A traditional chatbot answers each message with a single model call and forgets its mistakes. An AI agent, in contrast, is characterised by the following properties, each of which is related below to this project.

- **Autonomy.** After a question is submitted, Hybrid Analyst decides without further prompting whether to read policy documents, query the database or do both, writes its own SQL, and recovers from its own errors. Autonomy is deliberately bounded: the agent may retry at most three times and must stop and ask a human before touching sensitive columns.
- **Planning.** A router node classifies each question into one of three fixed execution paths (SQL, DOCS or BOTH) and rewrites follow-up questions into standalone ones. This is task decomposition into predefined paths, not open-ended dynamic planning (see Section 5.2).
- **Reasoning.** The LLM reasons inside three nodes (routing, SQL generation and answer synthesis), while the decisions between nodes are made by deterministic rules that read the state, for example "retry if the SQL failed and fewer than three retries were used".
- **Tool usage.** The agent uses four tools: a document retriever, a schema and example retriever, a SQL validator and a read-only SQL executor. The graph invokes them; the LLM does not issue native function calls (see Section 5.3).
- **Memory.** Conversation state is kept per thread by a LangGraph checkpointer so that a question such as "and in 2018?" is understood from the previous turn. Long-term memory is not implemented.
- **Goal-oriented execution.** Each question is a goal ("answer this, using only supported evidence"), and the graph runs until it reaches an answer, a refusal or a defined failure.

## 1.2 Background

Companies keep the facts of their business in relational databases and the rules of their business in documents. A refund policy states that a monthly cancellation rate above two percent triggers an investigation; the database says what the cancellation rate actually was. An analyst who is asked "was last month's cancellation rate a problem?" must find the right tables, write a correct query, find the right policy paragraph, and combine both into an answer. Conventional business-intelligence dashboards answer only questions their builders anticipated, and ad-hoc analysis requires SQL skills and knowledge of where each policy is written.

Text-to-SQL systems reduce the first difficulty by letting an LLM write the query from a natural-language question. The simplest design pastes the whole schema into one prompt and executes whatever comes back. That design has three weaknesses that motivate an agentic approach: it cannot use documents, it has no defence against unsafe or malformed SQL, and it cannot recover when the query fails. An agentic design adds a router that picks the right sources, tools that validate and safely execute queries, a feedback loop that repairs failed queries, a retrieval pipeline for documents, memory for follow-up questions, a human approval step for sensitive data, and a trace of everything that happened. This project builds and measures such a system.

## 1.3 Problem Statement

The objective of this project is to develop an Agentic AI-based system that answers business questions about an e-commerce marketplace by combining Text-to-SQL over a relational database with retrieval over company policy documents. Existing systems either answer only from data (single-prompt Text-to-SQL chatbots and dashboards) or only from text (document chatbots), execute generated SQL without safety checks, and give the user no record of how an answer was produced. Therefore, there is a need for a system that can decide which sources a question needs, query data safely and repair its own mistakes, ground policy statements in retrieved documents, pause for human approval when sensitive data is involved, and record every step so that its behaviour can be measured.

## 1.4 Motivation

**Why the problem was selected.** Questions that mix data and policy are common in operations and finance work ("is our late-delivery rate within target?", "does this cancellation rate trigger an escalation?"). They are exactly the questions that neither a pure SQL chatbot nor a pure document chatbot can answer.

**Why automation is required.** Answering such a question by hand means locating tables, writing and debugging SQL, finding the policy, and reconciling the two. Automating the routine parts frees the analyst to interpret the result.

**Why Agentic AI is suitable.** The work is a sequence of decisions and actions with feedback: choose sources, act, observe an error, correct, continue. That is the structure of an agent. A fixed pipeline cannot choose between data and documents per question, and a single prompt cannot recover from a failed query.

**Who will benefit.** Business analysts, operations managers and students who need quick, traceable answers over a database and a document set without writing SQL.

**Limitations of existing approaches that motivated the project.** Single-prompt Text-to-SQL has no validation, no retry and no document access; our own baseline in Chapter 9 confirms this. Document chatbots cannot compute numbers. Neither explains itself, and neither protects personal data.

## 1.5 Objectives

1. To design and implement an Agentic AI system, *Hybrid Analyst*, that answers business questions over the Olist e-commerce database and a set of company policy documents.
2. To implement autonomous task routing and execution, including a bounded SQL repair loop of at most three retries.
3. To integrate tools for schema retrieval, document retrieval, SQL validation and read-only SQL execution.
4. To implement retrieval-augmented generation over policy documents and per-thread conversation memory for follow-up questions.
5. To add a human-in-the-loop approval step for queries that read sensitive columns, and to record a structured trace of every step.
6. To evaluate the system with a 30-question test set and a single-prompt baseline, and to analyse its effectiveness and limitations using only measured results.

## 1.6 Scope of the Project

**Target users.** Business analysts and students who ask questions in English about marketplace operations.

**Supported tasks.** Questions about orders, deliveries, payments, reviews, sellers, products and categories (answered from the database); questions about refund, delivery, seller and review policies and metric definitions (answered from documents); and questions that need both.

**Functional scope.** Routing, SQL generation, validation and read-only execution with bounded repair, document retrieval, answer synthesis with source citations, approval for sensitive queries, per-thread memory, a Streamlit chat interface, structured traces, and an evaluation harness.

**Technologies covered.** Python, LangChain, LangGraph, SQLite, ChromaDB, Sentence-Transformers, sqlglot, Streamlit, pytest, and free-tier LLMs (Groq and Google Gemini were used; a local Ollama option exists in the configuration but was not tested).

**Expected usage.** A local application run with Streamlit on a developer machine for demonstration and study.

**Current limitations.** The data is a single public dataset covering 2016 to 2018; the six policy documents are synthetic; the dataset has no refunds table, so cancellations and low review scores are used as proxies; conversation memory is held in process memory and is lost when the application restarts; there is no long-term memory, no multi-agent collaboration and no reviewer step; and answer quality depends on a free-tier LLM whose latency and rate limits vary.

## 2.3 Research Gap

Most Text-to-SQL research evaluates query generation on benchmark databases in isolation. In practice, business questions often need an answer that joins database facts with the wording of internal policies, and a deployed system must also validate queries, protect personal data and explain how an answer was reached. We found fewer worked, measured examples that combine these concerns in one small, reproducible system that a student team can run on free tools.

This project does not claim a new algorithm. It is an applied integration. Its contribution is a working agentic workflow that (a) routes each question to data, documents or both, (b) validates and safely executes generated SQL with a bounded repair loop, (c) retrieves policy passages with source citations, (d) pauses for human approval on sensitive columns, (e) records a structured trace of every step, and (f) is evaluated honestly against a baseline, including a full list of the cases in which it fails.

# CHAPTER 3 – PROPOSED SYSTEM

## 3.1 Proposed Solution

Hybrid Analyst is a single-agent workflow implemented as a LangGraph state graph. Its parts are as follows.

- **User interaction.** A Streamlit chat page. Each browser session has its own conversation (thread) identifier, and the page shows Approve and Reject buttons when a query needs approval.
- **Agent.** The compiled graph, which holds a shared state and moves between ten nodes: router, retrieve_docs, retrieve_schema, generate_sql, validate_sql, approval, execute_sql, synthesize, out_of_scope and fail.
- **LLM.** One configuration module selects Groq or Google Gemini (a local Ollama option is coded but untested), so the provider can be swapped by editing an environment file. The LLM is used for routing, SQL generation and answer writing.
- **Planning.** The router classifies the question as SQL, DOCS, BOTH or OUT_OF_SCOPE and rewrites follow-ups into standalone questions.
- **Reasoning.** The LLM reasons about what to retrieve and write; rule-based edge functions decide what happens next (retry, ask for approval, execute, answer or fail).
- **Tools.** A document retriever, a schema retriever, a SQL validator and a read-only SQL executor.
- **Memory.** A checkpointer keeps the conversation per thread so that follow-up questions can be resolved.
- **Knowledge base and retrieval.** A SQLite database with the Olist e-commerce data, and a ChromaDB store holding the policy documents, the schema notes and twelve example question and SQL pairs. They are searched with local embeddings and a relevance threshold.
- **Execution.** Generated SQL is validated, executed read-only with a ten-second timeout and, if it fails, sent back to the LLM together with the error.
- **Final response.** A grounded answer that cites document file names and says plainly when data is missing.

## 3.4 Non-Functional Requirements

**Accuracy.** The system should return results that match a reference query or reference document. Measured accuracy on the 30-question test set is {m:accuracy}, and SQL accuracy is {m:sql_acc} (Chapter 9). Answers must be grounded: the synthesis prompt forbids using anything other than the returned rows and retrieved passages.

**Reliability.** Failures are handled, not hidden. A bad query is retried up to three times; a crashed node, exhausted retries or a declined approval end in a defined failure state with a plain-language message. In the evaluation run, {m:completion} of non-safety questions ended with an answer.

**Performance.** The mean end-to-end time was {m:mean_latency} seconds per question; SQL-only questions averaged {m:lat_sql} seconds and hybrid questions {m:lat_hybrid} seconds, dominated by LLM latency (Section 9.2).

**Scalability.** The design is intended for one user on one machine. The checkpointer stores conversations in process memory, the vector store is a local file-based Chroma database, and one graph instance is shared by browser sessions. Scaling to many users would need a persistent checkpointer and a server-based vector store.

**Security.** Database access is read-only and limited to an allow-list of tables; SQL is parsed and validated before execution; sensitive columns need human approval; API keys are kept only in a local `.env` file that is excluded from version control. The measured safety result is in Chapter 9, together with its limits.

**Usability.** The interface shows the answer, the SQL, the result table, the document sources and an expandable trace, and uses plain-language messages for errors, empty results and out-of-scope questions.

**Maintainability.** The code is split into small, named modules; the LLM and embedding choices live in a single configuration module; prompts are plain text files; and an automated test suite covers the tools, the graph, the interface and the evaluation harness ({c:tests_summary}).
